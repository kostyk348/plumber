plumber.
Обзор Установка Правила Протокол В системе

Plan 9, 1992 → сегодня

Программа говорит, что у неё за текст.
Правила решают, кто его откроет.

plumber — один демон и один текстовый файл правил вместо интеграций «каждый с каждым». Строка из лога main.rs:42 открывает редактор на сорок второй строке, manual.pdf:7 — документ на седьмой странице, номер детали — каталог. Программы при этом не знают друг о друге.

Установить Файл правил Исходники на GitHub

Одно сообщение — один маршрут

# любой процесс: «вот текст, разберись»
$ plumb send "src/main.rs:42"
OK edit                       # правила решили: существует такой файл → редактор, строка атрибутом

$ plumb send "https://9fans.net"
OK web                        # это URL → браузер

$ plumb send "manual.pdf:7"
OK pdf                        # это PDF со страницей → просмотрщик на странице 7

$ plumb send "какой-то набор букв"
ERR no rule matched this message

Отправитель не выбирает программу и не знает путей — он говорит только, что за данные у него в руках. Куда они поедут, решает файл правил, и решает его владелец, а не автор каждого приложения.

Почему это, а не N×M интеграций

Обычная интеграция — договор между двумя программами: просмотрщик логов знает про редактор, каталог знает про браузер, и каждая пара пишется руками. Пять программ — двадцать пять связей. Plumber убирает связь: программа отдаёт текст в одно место, а что с ним делать — дело правил.

N×M → N+M

Чтобы подключить новый редактор, браузер или каталог, не меняют ни одного отправителя. Правило в файле плюс читатель порта. Десять отправителей и десять получателей: было сто интеграций, стало двадцать.

Контекст решает смысл

XB-24 — номер детали и идёт в каталог. XB-24.pdf:3 — документ и идёт в просмотрщик на страницу 3. XB-24.rs:11 — файл и идёт в редактор. Решают правила: тип, содержимое и то, существует ли файл на диске.

Маршрутизация — это файл

Что куда попадает, видно в одном текстовом файле: его можно прочитать, обсудить, положить в git и ограничить. Это же и граница безопасности: plumb start — исполняемое содержимое, поэтому запуск команд выключен без --allow-start.

И для человека, и для скрипта

Отправитель — любая программа, которая умеет печатать в сокет: сборка, тест, скрипт, агент. Поэтому сломанная строка из CI открывается тем же правилом, что и из лога.

Из чего это состоит

ЧастьЧто делает
plumberd Демон: loopback-сокет, порты и читатели, перезагрузка правил по времени изменения, удержание сообщения для plumb client, файл с номером порта. Протокол — пять команд.
plumb Клиент: send, read, ports, rules и test — сухой прогон правил без демона вообще.
plumber-open Читатель, который открывает: подставляет {file}, {line}, {page}, {attr:name} в команду порта; --dry-run показывает, что запустилось бы.
plumbing Файл правил: наборы через пустую строку, объекты src dst wdir type attr data arg, глаголы is isfile isdir matches set add delete, действия plumb to start client hide, макросы и include.

Сообщение — семь полей из plumb(6) 1992 года: src, dst, wdir, type, attr, ndata, data. Формат байт в байт как в оригинале, поэтому проверить его можно глазами.

Попробовать за минуту

# собрать (Rust 1.80+)
cargo build --release

# демон: правила и файл, куда положить номер порта
./target/release/plumberd --rules plumbing.example --port-file /tmp/plumb.port

# читатель порта edit — то, что делает редактор
./target/release/plumb read edit

# в другом терминале: отдать адрес
./target/release/plumb send "src/main.rs:42"

# спросить у правил, что будет, без демона
./target/release/plumb test --rules plumbing.example "https://9fans.net"
Правила — исполняемое содержимое: plumb start умеет запускать команды, поэтому он выключен по умолчанию. Файл правил держите там, где его не правит кто попало.

Честно о состоянии

0.3 Работает: формат сообщения, грамматика правил, доставка копии каждому читателю, перезагрузка правил по mtime, удержание сообщения для plumb client, открытие портов с подстановками, CLI и 27 тестов, включая запуск настоящего plumberd и обмен по сокету.

не сделано Нет встроенных читателей под конкретные редакторы («прыгнуть на строку в VS Code» — это шаблон команды порта, а не магия). Нет GUI и нет интеграции с файловыми менеджерами из коробки — для этого есть .desktop и MIME, см. «В системе». Транспорт — loopback TCP, а не монтируемый файловый сервер: у Windows нет per-process mount.
