plumber.
Обзор Установка Правила Протокол В системе

Справочник

Файл правил

Обычный текст. Наборы правил отделены пустой строкой; срабатывает первый набор, у которого совпали все условия, поэтому частное пишут выше общего.

Скелет

# макрос: раскрывается при чтении файла
addr=':([0-9]+)'

type is text
data matches '([.a-zA-Z0-9_/\\-]+)('$addr')?'
arg isfile $1
data set $file
attr add addr=$2
plumb to edit

Каждая строка — «объект, глагол, аргумент». Первая тройка проверяет сообщение, вторая его меняет, plumb говорит, куда его деть.

Объекты

ОбъектЧто проверяет или меняет
srcимя отправителя
dstпорт, на который сообщение уже попало
wdirрабочий каталог отправителя — база для относительных путей
typeтип содержимого: text, image, …
attrпары вида line=42, page=7
dataсам текст сообщения
argаргумент глагола: что именно проверять (arg isfile $1)

Глаголы

ГлаголСмыслПример
isточное равенствоtype is text
matchesрегулярное выражение; $1…$n — захватыdata matches '([^ ]+)\.rs:([0-9]+)'
isfileпуть существует и это файл (относительно wdir)arg isfile $1
isdirпуть существует и это каталогarg isdir $1
setзаменить содержимое объектаdata set $file
addдобавить атрибутattr add line=$2
deleteудалить атрибутattr delete addr

isfile и isdir — это то, что делает правила умнее регулярных выражений: README.md уходит в редактор, только если такой файл правда есть рядом с отправителем.

Действия

ДействиеЧто делает
plumb to ПОРТотправить сообщение на порт. Основное действие.
plumb client КОМАНДАназвать клиента порта: если никто не слушает, сообщение ждёт, пока он откроет порт.
plumb start КОМАНДАзапустить команду. Выключено без --allow-start: файл правил — исполняемое содержимое.
plumb hideне передавать сообщение дальше (глушилка для шумных отправителей).

Подстановки

ЗаписьЗначение
$0, $1, …захваты последнего matches ($0 — всё совпадение)
$fileпуть, разрешённый из захвата: $wdir + путь
$dirкаталог файла
$wdirрабочий каталог отправителя
$src, $dst, $typeполя сообщения
Набор правил кончается пустой строкой или строкой комментария. Это осознанное отличие от Plan 9: не «комментарии игнорируются везде», а «комментарий — тоже граница набора», чтобы разбитый на абзацы файл читался как оглавление. Проверить, что получилось, — plumb test.

Рецепты

Все примеры ниже прогнаны через plumb test — это не пожелания, а рабочий файл.

Файл со строкой → редактор

type is text
data matches '([.a-zA-Z0-9_/\\-]+)('$addr')?'
arg isfile $1
data set $file
attr add addr=$2
plumb to edit

Голое имя файла (без слэша)

Cargo.toml — существующий файл, но в нём нет ни одного /, поэтому правило выше его не поймает, а правило доменов — поймает: .toml выглядит как зона. Это правило ставится выше доменов, и arg isfile оставляет example.com в покое. 

type is text
data matches '^([.a-zA-Z0-9_+\-]+\.[a-zA-Z0-9]+)('$addr')?$'
arg isfile $1
data set $file
attr add addr=$2
plumb to edit

Ссылка → браузер

type is text
data matches '^(https?|ftp)://'
plumb to web

PDF со страницей → просмотрщик

Это правило обязано стоять выше файлового: manual.pdf:7 — тоже существующий файл, и общее правило съело бы его первым. 

type is text
data matches '([.a-zA-Z0-9_/\\-]+\\.pdf)('$addr')?'
arg isfile $1
data set $file
attr add page=$2
plumb to pdf

Каталог → файловый менеджер

type is text
data matches '^([.~/a-zA-Z0-9_\\-]+)$'
arg isdir $1
data set $file
plumb to dir

Объект git → git show

Здесь нужен plumb start: у порта нет долгоживущего читателя, команда одноразовая. Демон запускается с --allow-start. 

type is text
data matches '^([0-9a-f]{7,40})$'
plumb start git --no-pager show $1 --stat

Сообщение ждёт своего читателя

type is text
data matches '^XB-([0-9]+)$'
plumb to catalog
plumb client catalog-gui {data}

Если каталог ещё не запущен, сообщение не теряется: оно придерживается и приходит тому, кто откроет порт catalog позже.

Отладка правил

Демон не нужен: plumb test читает файл правил и показывает, что случилось бы.

$ plumb test --rules plumbing "src/main.rs:42"
rule: line 10
port: edit
--- message the receiver gets ---
plumb-test
edit
/tmp/cook
text
addr=:42

21
/tmp/cook/src/main.rs

Это не «красивый вывод», а настоящее сообщение: src, dst, wdir, type, атрибуты, пустая строка, длина data и сам data. Ровно то, что получит читатель порта. 

$ plumb test --rules plumbing "https://9fans.net"
rule: line 12
port: web
…
$ plumb test --rules plumbing "просто текст"
no rule matched: this message would be discarded

Четыре грабли, на которые наступают все

  1. Правило с isfile не сработает на несуществующий файл. plumb test запускается из текущего каталога, поэтому src/main.rs:42 попадёт в редактор только там, где этот файл есть. Для логов из CI это значит: держите отдельное правило без isfile (см. рецепт выше).
  2. Порядок решает. manual.pdf:7 — существующий файл, поэтому правило PDF обязано стоять выше файлового, иначе его заберёт редактор с addr=:7.
  3. Пустой захват даёт пустой атрибут. На src/main.rs без номера строки получится addr=; читатель должен это терпеть (наш — терпит).
  4. Макрос со скобками съедает нумерацию захватов. Это самая коварная: макрос раскрывается в текст регулярного выражения, поэтому addr=':([0-9]+)' добавляет в вашу регулярку свою группу. В правиле data matches '([a-z]+(/[a-z]+)+)('$addr')?' группа ([a-z]+(/[a-z]+)+) содержит ещё и внутреннюю (/[a-z]+) — и $2 указывает уже на неё, а не на адрес. Проверка занимает секунду: 
$ plumb test --rules plumbing "src/open.rs:60"
…
addr=/open.rs          # ← вот это $2: внутренняя группа, а не «:60»
21
src/open.rs

Лечится одной привычкой: свои вложенные группы пишите как (?:…), тогда $1, $2, … считаются только там, где вы этого ждёте, и макросы остаются безопасными.

Пустой вывод при непустом файле правил почти всегда значит одно: набор развалился на лишней пустой строке или комментарии посередине. plumb rules (через демон) покажет, какой текст он на самом деле разбирает.
